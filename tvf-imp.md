# Task: Correct SEO handling for the Travel Finder filtered URLs

We need to improve the SEO/crawler behaviour of the WordPress Travel Finder plugin, specifically for filtered URLs such as:

`/ou-partir-trouvez-votre-prochain-voyage/?f=kids,france`

The current frontend class is `TVF_Frontend`.

The site has now also been configured in `robots.txt` to disallow filtered Travel Finder URLs:

```text
Disallow: /ou-partir-trouvez-votre-prochain-voyage/?f=
```

Do not modify `robots.txt` as part of this task.

## Goals

Implement the following behaviour:

1. Filter/chip links generated by the Travel Finder must have `rel="nofollow"`.
2. Real links to travel articles/results must remain normal followed links.
3. Do not output `<link rel="canonical">` or `<meta name="robots">` from inside shortcode HTML/body content.
4. Filtered Travel Finder URLs should canonicalize to the clean permalink of the Travel Finder page.
5. Filtered Travel Finder URLs should be `noindex,follow`.
6. Avoid duplicate canonical tags or duplicate/conflicting robots meta tags.
7. Prefer WordPress's existing SEO/canonical mechanisms and filters rather than manually emitting duplicate tags.
8. Preserve current multilingual behaviour, REST API behaviour, filtering behaviour and JavaScript functionality.

---

# 1. Add `rel="nofollow"` to filter links

The current method is:

```php
private static function chip_html(
    string $slug,
    string $label,
    array $selected,
    string $base_url,
    array $dead_slugs = []
): string
```

It currently generates anchors similar to:

```html
<a href="...?f=..." class="tvf-chip ...">
```

Change the generated anchor so every filter-chip link contains:

```html
rel="nofollow"
```

For example:

```html
<a href="...?f=..." rel="nofollow" class="tvf-chip ...">
```

This applies both to selecting and deselecting filters.

Keep all existing attributes and behaviour:

- `class`
- `role="checkbox"`
- `aria-checked`
- `aria-disabled`
- `tabindex`
- `data-slug`

Do not otherwise alter chip behaviour.

## Important

Do NOT add `nofollow` to links to actual travel articles generated in `render_cards()`.

These links:

```php
echo '<span class="mv-tile__title"><a class="mv-tile__link" href="' . esc_url( $url ) . '">'
```

must remain ordinary followed internal links.

The reset link back to the clean Travel Finder page should also remain followed.

# 2. Remove SEO tags from shortcode output

The current `render_shortcode()` contains:

```php
<?php if ( $selected ) : ?>
    <link rel="canonical" href="<?php echo esc_url( $base_url ); ?>">
    <meta name="robots" content="noindex,follow">
<?php endif; ?>
```

Remove this block completely.

Reason:

The shortcode is rendered inside `the_content`, so these elements are currently being emitted in the HTML `<body>` rather than correctly handled in the document `<head>`.

Do not replace this block with another manually echoed `<link>` or `<meta>` block inside the shortcode.

# 3. Canonical behaviour

Filtered Travel Finder URLs should canonicalize to the normal clean permalink of the current WordPress page.

Example:

Filtered URL:

```text
https://www.mamanvoyage.com/ou-partir-trouvez-votre-prochain-voyage/?f=kids,france
```

Canonical:

```text
https://www.mamanvoyage.com/ou-partir-trouvez-votre-prochain-voyage/
```

The canonical must NOT contain:

- `f`
- tracking parameters such as `utm_source`
- unrelated request query parameters
- filter ordering

Use the actual WordPress permalink:

```php
get_permalink( $post )
```

rather than deriving the canonical from the current request with:

```php
remove_query_arg( 'f' )
```

The existing `base_url()` function may continue to use `remove_query_arg( 'f' )` for UI/navigation purposes. Do not change that unless required.

# 4. Prefer filtering the existing WordPress canonical

Do not blindly output an additional canonical using `wp_head`.

First inspect how this WordPress installation currently produces canonical tags.

Potential sources include:

- WordPress core `rel_canonical()`
- an SEO plugin
- the theme
- another custom plugin

The implementation must result in exactly one effective canonical tag.

If WordPress core canonical handling is being used, prefer the `get_canonical_url` filter.

Register it in `init()`:

```php
add_filter(
    'get_canonical_url',
    [ __CLASS__, 'filter_canonical_url' ],
    10,
    2
);
```

Implement something along the lines of:

```php
public static function filter_canonical_url( string $canonical, WP_Post $post ): string {
    if ( ! self::is_travel_finder_post( $post ) ) {
        return $canonical;
    }

    if ( ! self::has_filter_request() ) {
        return $canonical;
    }

    return get_permalink( $post );
}
```

Feel free to structure this differently if appropriate.

The important requirement is:

- normal Travel Finder URL → normal canonical behaviour
- filtered Travel Finder URL → clean Travel Finder permalink

Do not affect canonical URLs for other posts/pages.

# 5. Detect Travel Finder pages robustly

The code currently uses:

```php
global $post;

if (
    ! is_a( $post, 'WP_Post' )
    || ! has_shortcode( $post->post_content, 'travel_finder' )
) {
    return;
}
```

It would be good to centralize this logic in a helper so asset loading and SEO logic use the same determination.

For example:

```php
private static function is_travel_finder_post( $post ): bool
```

Possible implementation:

```php
private static function is_travel_finder_post( $post ): bool {
    return is_a( $post, 'WP_Post' )
        && has_shortcode( $post->post_content, 'travel_finder' );
}
```

Then `enqueue_assets()` and SEO callbacks can use that helper.

This refactoring is optional but preferred because it avoids slightly different detection logic appearing in several places.

# 6. Detect a real `f` filter request

Do not simply use:

```php
! empty( $_GET['f'] )
```

without sanitization if avoidable.

Reuse the plugin's existing filter parser.

Suggested helper:

```php
private static function requested_filters(): array {
    $f = isset( $_GET['f'] )
        ? sanitize_text_field( wp_unslash( $_GET['f'] ) )
        : '';

    return self::parse_filter_param( $f );
}
```

Then:

```php
private static function has_filter_request(): bool {
    return ! empty( self::requested_filters() );
}
```

This has an important benefit:

A malformed URL like:

```text
?f=
```

or a string containing no valid registered filter slugs should not unnecessarily trigger filtered-page SEO behaviour.

Use the same interpretation of filters that the Travel Finder itself uses.

# 7. `noindex,follow` handling

Filtered Travel Finder URLs should produce:

```html
<meta name="robots" content="noindex,follow">
```

in the `<head>`.

However, do NOT simply emit an additional robots meta tag if WordPress, the theme or an SEO plugin already controls robots directives.

Use WordPress's robots API where possible.

Modern WordPress provides the `wp_robots` filter.

Register:

```php
add_filter(
    'wp_robots',
    [ __CLASS__, 'filter_robots' ]
);
```

Suggested implementation:

```php
public static function filter_robots( array $robots ): array {
    global $post;

    if (
        ! self::is_travel_finder_post( $post )
        || ! self::has_filter_request()
    ) {
        return $robots;
    }

    $robots['noindex'] = true;
    $robots['follow']  = true;

    return $robots;
}
```

Verify the exact WordPress API semantics for `wp_robots` on the installed WordPress version before committing.

The final HTML should effectively convey:

```text
noindex,follow
```

Do not remove unrelated existing robots directives unless they directly conflict.

For example, preserve existing values such as:

- `max-image-preview`
- `max-snippet`
- `max-video-preview`

if present.

Do not accidentally convert a site-wide robots policy.

# 8. Interaction with robots.txt

The filtered URLs are now blocked through:

```text
Disallow: /ou-partir-trouvez-votre-prochain-voyage/?f=
```

Keep the canonical and `noindex` handling anyway.

Reasons:

- not all crawlers obey robots.txt
- a crawler may already know filtered URLs
- this makes the page semantically correct when fetched
- robots.txt may change later

Be aware that a crawler obeying robots.txt may not fetch the filtered page and therefore may not see its canonical or noindex directive.

This is expected.

The primary protections are therefore:

1. `rel="nofollow"` on generated filter links
2. robots.txt disallow
3. canonical fallback
4. `noindex,follow` fallback

# 10. Important canonical edge cases

Please test these cases.

### Clean page

Request:

```text
/ou-partir-trouvez-votre-prochain-voyage/
```

Expected:

- normal page canonical
- indexable
- no Travel Finder-specific `noindex`

### One filter

```text
/ou-partir-trouvez-votre-prochain-voyage/?f=kids
```

Expected canonical:

```text
/ou-partir-trouvez-votre-prochain-voyage/
```

Expected robots:

```text
noindex,follow
```

### Multiple filters

```text
/ou-partir-trouvez-votre-prochain-voyage/?f=kids,france,ete
```

Same expected canonical and robots behaviour.

### Filter + tracking parameter

```text
/ou-partir-trouvez-votre-prochain-voyage/?f=kids,france&utm_source=facebook
```

Expected canonical:

```text
/ou-partir-trouvez-votre-prochain-voyage/
```

Do NOT canonicalize to:

```text
/ou-partir-trouvez-votre-prochain-voyage/?utm_source=facebook
```

### Reordered filters

Both:

```text
?f=kids,france
```

and:

```text
?f=france,kids
```

must canonicalize to the same clean URL.

### Empty filter

```text
?f=
```

Treat this as the clean/default finder state unless existing parsing behaviour dictates otherwise.

Do not unnecessarily mark it `noindex`.

### Invalid filters

Example:

```text
?f=this-does-not-exist
```

Use the existing parser's result.

If no valid filters remain after parsing, preferably treat the request as unfiltered rather than applying filtered-page SEO rules.

### Other site page

A completely unrelated WordPress post/page must have exactly the same canonical and robots behaviour as before this change.

# 12. Avoid duplicate SEO tags

After implementing the change, inspect the rendered `<head>` of:

1. clean finder page
2. filtered finder page
3. ordinary article

For each, confirm:

### Canonical

There should be exactly one:

```html

```

or otherwise one unambiguous canonical generated by the site's SEO system.

There must NOT be:


simultaneously.

### Robots

There should be only one coherent robots policy.

Do not produce conflicting tags such as:

```html

<meta name="robots" content="noindex,follow">
```

If an SEO plugin owns robots output, integrate with its filters/API rather than outputting another tag.
